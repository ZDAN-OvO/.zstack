## 一、先确认瓶颈是不是 SQL

P99 从 200ms 涨到 900ms 这个形态，值得先怀疑一下归因：

- **P50 有没有一起涨？** 只有 P99 涨、P50 基本持平 → 大概率不是"SQL 变慢了"，而是排队或抖动：连接池被打满、偶发锁等待、GC、下游超时重试、缓存集中失效。
- 同期有没有发布、数据量增长、流量变化、慢查询告警？
- **这个接口一次请求实际打了几条 SQL？** N+1 很常见，单条都"不慢"，但一次请求 20 条，P99 就是长尾。

如果 P50 和 P99 一起涨，那才是单条 SQL 本身退化，继续看第二部分。

## 二、需要你提供的东西

1. **慢 SQL 原文，带真实参数值**（脱敏可以）。用 ORM 的话请给最终生成的 SQL，不是链式调用代码。
2. **执行计划**：MySQL 用 `EXPLAIN ANALYZE`，PG 用 `EXPLAIN (ANALYZE, BUFFERS)`。我要看的是估算行数 vs 实际行数、`type=ALL`、`Using filesort` / `Using temporary`、有没有回表。
3. **涉及表的 DDL**（`SHOW CREATE TABLE`），含现有索引和字段类型。别只说"有索引"——索引的列顺序和区分度决定一切。
4. **数据量级**：这几张表各多少行，以及这条 SQL 实际返回多少行。200ms 变 900ms 最常见的原因就是某张表涨过了阈值，执行计划翻转。
5. **这个接口的 handler / service 代码片段**，我要看有没有循环里查询、`select *`、事务里做非必要的查询。

## 三、等数据回来之前，可以先说的判断方向

- 4.5 倍的涨幅，按概率排：数据量过阈值导致索引失效或计划翻转 > 锁等待 > 查询次数随数据放大 > 连接池与慢 SQL 互相放大。
- 优化优先级：**先砍查询次数**（N+1、重复查、能合并的合并）> 补/改索引 > 改写 SQL（别在索引列上套函数、拆 OR、深分页改游标）> 加缓存。缓存放最后，它经常只是把问题藏起来，下次换个形态再爆。

## 四、两个边界问题

- 能改索引吗（有没有 DDL 窗口 / 在线变更工具）？还是只能改 SQL 和代码？
- 是线上还是预发？改完你怎么验证——有可回放的流量或压测环境吗？
