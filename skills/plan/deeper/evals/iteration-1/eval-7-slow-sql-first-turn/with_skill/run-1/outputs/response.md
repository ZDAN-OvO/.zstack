先不动 SQL。工作目录我看过了，是空的——没有 SQL 文件、没有代码、没有日志，所以你说的"这几个慢 SQL"我一条都还没看到。

拿到具体语句之前，有两个问题会直接决定后面给你什么建议：

❓ **Q1** - **900ms 里 SQL 占多少**：P99 从 200 涨到 900，可能是 SQL 本身变慢，也可能是同一批 SQL 被调了更多次（循环里查、N+1）、连接池排队、锁等待、缓存失效、数据量涨了，或者这次上涨跟着某次发布/流量变化来。这几种修法完全不同，改 SQL 只治第一种。你有没有看过这个接口的耗时构成——APM 的 span 树里 SQL 那段花了多少，或者慢查询日志里它对应的语句实际执行多久？

- (a) 有 trace，能看到 SQL 占比
- (b) 只有慢查询日志，知道哪几条语句慢，但不知道它们占接口多少
- (c) 都没有，是告警或同事说"SQL 慢"

➡️ 建议按 (a) 走：挑一个最慢的真实请求，看它整条链路的 span，把 SQL 耗时加总。如果 SQL 总共只占 200ms，优化 SQL 的天花板就是那 200ms，剩下的得去别处找。这一步一般半小时内能做完。

---

❓ **Q2** - **你手上有哪些材料，能动到哪一层**：我要的原始材料，按重要性排：

1. 慢 SQL 原文，带真实参数值——分页深度、时间范围、IN 列表长度都会改变执行计划，去掉参数的 SQL 常常看不出问题；
2. 一条能复现的执行计划（`EXPLAIN`，最好 `EXPLAIN ANALYZE`）——能不能在只读从库或预发上跑？生产上跑 ANALYZE 有代价，这点先定下来；
3. 最近两到四周的变更：数据量增长、加/删索引、上线、连接池或 optimizer 参数调整、表结构变更；
4. 慢查询日志的配置：阈值多少、全量还是采样（这决定你手上那份"慢 SQL 列表"可不可信）；
5. 已经试过什么、结果如何：加过索引？改过 SQL？被回滚过？

另外两个边界：多久要出结果，以及你能动到哪一层——只改 SQL？能加索引？能改表结构或加缓存？谁批准？

➡️ 建议先只给第 1、2、3 项。有语句、执行计划和变更记录，大多数情况当场就能判断方向；慢日志配置和"试过什么"等看完再补，不用一次凑齐。

答完这两问，我再把专家会怎么查这个问题的完整打法摊开给你，你逐条留或扔。现在直接改 SQL 是猜。
