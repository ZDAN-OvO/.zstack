# 交接单：季报监测规则草案（Rung 3）

来源：`ladders/q-report-numbers.md`（阶梯记录）。本单只定义要交出去的任务，不定义技法。

## 一句话

用现有 2 个季度的 BI 导出数据，输出一份"季报指标监测规则草案"，并在草案中逐条标明回测样本不足。

## 交付物

单个文件 `drafts/监测规则草案.md`，包含四部分：

1. **指标清单**：与季报模板字段一一对应，标注口径（金额/比率/计数量）与数据来源 CSV 列。
2. **显著变化判定**：每个指标的阈值与算法（环比、同比、绝对值下限、连续两期同向等），写清为什么这样取。
3. **提醒机制**：触发条件、聚合与去重、频率上限（例如同一指标每季最多 1 次）、提醒正文必填字段；渠道留占位（邮件/IM 二选一，待定）。
4. **回测局限说明**：每条规则注明"依据样本：2 个季度"，并标出无法验证的部分——阈值误报率、漏报率、季节性影响、异常点是否真实异常。

## 验收标准

- 每个季报模板字段都在指标清单里有对应规则，或有明确的"不监测"理由。
- 每条规则都能回答："如果上季度用这条规则，会触发几次、分别在哪个月"——即使答案是"无法判断（样本不足）"，也要写出这句。
- 全文没有任何"已验证/试点证明有效"之类的表述；局限段与规则一一对应，不是笼统免责声明。
- 草案能被第三方直接拿去跑一遍历史数据核对，不需要再问作者。

## 已知风险

- 2 个季度 = 2 个数据点，多数统计口径（同比、季节调整、分布尾部）根本算不出，草案的可信度上限就在这里。**不要用"行业经验值"包装成回测结论。**
- 如果管理层会需要的是"为什么这季度数字变了"（Rung 1）和"这三个预算决策怎么选"（Rung 2），Rung 3 不能替代它们，三份一起用。

## 下一步（执行方）

1. 拉本季度 + 上季度 CSV，对齐模板字段，列出可用列与空列。
2. 先写指标清单（第 1 部分），确认字段对得上再写规则，避免规则写完发现列不存在。
3. 规则写完后，把上季度真实数据套一遍，记录每条规则的触发结果（含"无法判断"）。
4. 局限段最后写，逐条对应前面的规则编号。
