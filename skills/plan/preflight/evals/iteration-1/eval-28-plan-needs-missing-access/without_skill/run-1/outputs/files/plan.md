# Plan：季度回顾 → 每日异常监控

**日期**：2026-11-10
**目标**：问题早发现——异常在变成季报里的坏数字前就提醒到老板。
**边界**：不发垃圾提醒。
**完成定义**：用历史数据证明它能比季报更早发现问题；然后与季报并行跑满一个季度。

---

## 1. 素材现状（先说实话）

| 素材 | 内容 | 能否支撑目标 |
|---|---|---|
| `data/q3-metrics.csv` | 3 行月粒度：revenue / new / churned / nps（2026-07~09） | **不够** |
| `notes/worklog.md` | 定性线索：8 月中试用期 14→7 天；9/8 起"太难上手"投诉变多 | 只能当作时间线对照 |
| `template.md` | 现有季报模板 | 作为并行期的对照组 |

两个硬缺口：

1. **粒度**：要给"每日"监控做证明，手上只有月粒度数据。3 个点既建不了基线，也做不了回测。
2. **断档**：Q4 已跑到第 6 周（10/1 起），但 `data/` 里没有 10 月、11 月任何数据。并行期已经在流逝。

所以第 0 阶段不是写代码，是**补数据**。这一步不通，后面的"证明更早"就是空话。

顺带一个观察（可直接用于验证）：Q3 的三个数字是同向恶化的——churn 12→19→24、NPS 38→31→27、revenue 182k→176k→171k；而工单投诉在 9/8 就出现了，试用期改动在 8 月中。**信号比季报早，但信号不在现有指标里**，而在工单文本里。这决定了监控必须包含"领先指标"，不能只盯财务报表上的四个数。

## 2. 阶段计划

### 阶段 0：补数据（阻塞项，1 周）

- [ ] 拉齐 **≥12 个月**（最好 24 个月）日粒度历史：revenue 按天、new/churn 按天、NPS（按周即可）、试用转化率（8/14 改试用期后口径已变，需分段处理）。
- [ ] 拉工单数据：日工单量、`太难上手 / onboarding / 复杂` 关键词命中数、首次响应时长。
- [ ] 明确口径与数据源表：谁产出、落到哪、更新频率、延迟多少天。
- [ ] 若某项历史确实拿不到（如早期工单没归档），**记下缺失区间并在回测中剔除**，不要用插值假装有数据。

**出口条件**：有一份 ≥12 个月的日粒度宽表，且已知每列的可得时间点（避免用"事后才有的数"做回测，那是自欺）。

### 阶段 1：定指标与基线（1 周）

指标分两层：

- **结果层**（老板认得）：revenue、churn rate、NPS、净留存。
- **领先层**（要早发现的其实是这些）：工单量与"难上手"占比、试用→付费转化、激活率、登录/使用频次。

基线方法（简单优先，能解释为止）：
- 同比 + 环比 + 滚动 8 周均值/标准差（z-score）。
- 月度指标按"当月至今累计 vs 上月同期"对比，避免月中看不出来。
- 季节性：B2B SaaS 有月末冲单，先按**工作日**对齐，再看周内模式。

### 阶段 2：告警规则 + 防垃圾（1 周）

边界是"不发垃圾提醒"，所以**先定预算，再定规则**：

| 约束 | 取值 |
|---|---|
| 提醒预算 | ≤1 条/月（均值），≤4 条/季，硬上限 |
| 触发门槛 | 偏离基线 ≥2σ **且** 幅度有业务意义（如 churn 环比 +30%） |
| 持续性 | 需连续 2 个周期同向确认，单点尖峰不报 |
| 去重 | 同一指标 14 天内不重复报；升级才再报 |
| 分级 | P1 立即推（收入/大客户流失）；P2 进每日摘要；P3 只在周报里 |
| 渠道 | 日常只进一份摘要；季度仍出季报，不新增第二个汇报入口 |
| 静默 | 明确"这一条为什么值得打扰老板"——每封信必须附：指标、偏离幅度、基线图、最可能原因、建议动作 |

**验收**：把 Q3 数据（及补齐的历史）喂进去，回放触发历史，**数一数总共会响几次**。超过预算的规则直接砍掉或调阈值。垃圾提醒不是靠自觉，是靠预算硬约束。

### 阶段 3：历史回放，证明"更早"（1~2 周）

定义**提前量** = 首次可信告警日期 − 季报暴露该问题的日期。

回放方法（按月步进，只用当时可得的数据，不看未来）：

1. 对每个月末，只用 ≤ 该月末的数据重算基线与告警。
2. 记录每个真实问题的首个告警日。
3. 与季报日（季末次月第一周）对比，得提前量。
4. 同时记录**误报数**——只报提前量不报误报，等于没测。

已知的三个"真实问题"可作为回放考点：churn 抬升、NPS 下滑、"太难上手"工单激增。预期结论大致是：工单信号 9 月上旬就能出、NPS/churn 要到月末或次月——**但这是待验证的假设，不是结论**。如果回放显示领先指标也没提前多少，那就如实写进报告，不硬凑。

**出口条件**：一份回测表（问题 / 首个告警日 / 季报暴露日 / 提前天数 / 期间误报数），以及一句话结论：值不值得继续。

### 阶段 4：与季报并行跑一个季度（Q4，至 12/31）

- 因为今天已是 11/10，并行期按 **11/10 → 2027-01-31** 计（覆盖一个完整季度，且向后顺延，避免只剩 7 周）。
- 全程照旧发季报，监控只在旁边跑、只在触发时发。
- 每周记一行：告警数、是否有效、老板是否觉得被打扰。
- 季度末对照：监控提前发现了哪些、漏了哪些、误报几条、季报里哪些信息是监控给不了的。

## 4. 风险与不做的事

- **3 个月数据 + 月粒度**是最大风险。回测说服力取决于补齐的历史质量，先解决这个。
- **别一上来上平台**：不需要新 BI 工具、不需要实时流。一张表 + 一个定时脚本 + 一份摘要够用。工具化留到回测证明有效之后。
- **不追求"每天看"**：老板不看日报是设计前提，不是缺陷。目标是"该响的时候响"。
- **接受误报存在**：0 误报意味着阈值高到漏报。用预算管理，不用完美管理。
- **工单文本依赖**：关键词法会漏同义表达，先用简单规则跑，效果不够再考虑分类模型——不要一开始就做 NLP 项目。
