# Brief: admin-console 迁不迁 React —— 全量重写 / 渐进迁移 / 不迁三条路线的代价与风险一页表

- Stage: explore
- Source: 「我们在考虑把 admin-console 从 Vue 迁到 React，还没决定迁不迁。想先看看有哪些路线：全量重写、渐进迁移、不迁，各自代价和风险。依据就用仓库代码和 package.json，不要引用网上的框架对比软文。不要给我写迁移代码。先给一页对比表就行。」

## Goal
- 服务「迁不迁」这个尚未决的决策：把三条路线各自的代价与风险并排摊开，让用户自己判断，而不是替用户判断。
- 交付的是选项与取舍，不是结论或推荐；用户的决策标准尚未确定，把这轮探索出来的差异交给用户去形成标准。
- 只比较「要不要、怎么迁」三种走法在本仓库的代价，不比较 Vue 与 React 本身孰优。

## Context
- 仓库 admin-console，`private: true`；唯一清单文件 [package.json](../../package.json) 只声明 dependencies：vue 3.4.21、vue-router 4.3.0、vuex 4.1.0、element-plus 2.6.1；无 react / react-dom，无 qiankun、wujie 一类微前端依赖。
- 该 package.json 没有 scripts、devDependencies、lockfile，也没有构建 / 测试 / lint 配置，因此打包方式、依赖能否顺利重建、测试能否保护迁移，仓库里查不到依据。
- 源码只有两个文件：[src/App.vue](../../src/App.vue)（`el-config-provider` 包住 `router-view`）与 [src/router/index.js](../../src/router/index.js)（注释称「40 个页面路由」，实际 `export default []`）。
- 所以「40 个页面」是注释里的声明，不是可核对的事实；路由表、页面组件、自研封装、Vuex store 均未提交，页面数量与 element-plus 使用深度无法由代码确认。
- 迁移动因、团队规模与 React 经验、时间窗口、有无其他 React 项目，仓库中都没有，属待确认输入，见 Open questions。

## Materials
- 只用本仓库：package.json 与 `src/` 下的实际文件；每个论断注明文件路径（可带行号）。
- 禁用网络框架对比文章、博客、迁移复盘、社区评测；不得用外部材料替代仓库证据，也不得用「业界普遍认为」补齐。
- 仓库查不到的事实（人力、工期、金额、页面真实数量、团队技能、构建产物大小）留空并标「仓库无法判定」，不估算、不套用行业均值。

## Boundaries
- 不写迁移代码、脚手架、目标目录结构、codemod 脚本；除本 brief 外不改动仓库任何文件。
- 不给推荐结论，不写「建议选 X」；可以说某路线在某维度更贵或更险，但必须同时写出它换来的东西。
- 不出现工时、人天、金额、百分比进度等无来源数字。
- 不做 Vue 对 React 的框架优劣评价，不假设仓库之外的条件（有 CI、有设计系统、有微前端基建、有独立前端团队）。
- 不把「不迁」写成陪衬：它同样要有真实收益与其自身代价（如长期双技术栈、招聘面变窄）。

## Done
- 一页 Markdown 对比表：3 行（全量重写 / 渐进迁移 / 不迁），列为 Assumptions 里默认的维度，每格不超过两句。
- 每格尽量带仓库证据（文件名、依赖名、注释原文）；无证据的格写「仓库无法判定」，不填推测。
- 表下一行「待你确认的口径」即可收尾：不写分析长文、不写实施步骤、不写推荐。

## Assumptions
- 对比维度默认取六列：改造工程量、团队技能匹配、工具链与组件替代（element-plus 等价物从哪来）、过渡期维护（双栈共存、路由/鉴权/状态共享）、回归风险与可逆性、长期收益；压不进一页时合并到四至五列。
- 「渐进迁移」默认按逐页替换、最终收敛到单栈（strangler）理解；双栈长期共存只作为过渡期形态在该行内一句带过。若 Q2 选另一口径，此行整段改写。
- Context 中未确认的动因、团队与时间不写成事实：涉及团队技能的格写「取决于团队 React 经验（未确认）」，不代为假定。
- 缺失数据处理同上：留空加「仓库无法判定」，不估算。
- 「一页」按一屏可读完理解（Markdown 表格），不要求导出 Word / PDF。
