## 2. 硬约束（用户明确下达，不可协商）

| # | 约束 | 含义 |
|---|------|------|
| C1 | 只改 `src/` 下的代码 | 源码写入范围限于 [src/](../../src/)。`package.json`、`docs/`、配置、CI 均在范围外——**新增依赖、改脚本、加配置文件都需要用户额外批准**，方案里须单列为「需要授权的动作」 |

## 3. 现状证据（已核实）

工作区极小，可用信息只有以下四项，均已逐字读取：

1. [package.json](../../package.json)：`order-service`，`private: true`，依赖 `express@4.19.2`、`pg@8.11.3`。无 `scripts`、无 `engines`、无测试框架、无 lockfile。
2. [src/checkout.js](../../src/checkout.js)：全文仅 3 行，是一个空壳函数：
   `// POST /checkout：串行查询库存、优惠券、地址，再写 orders 表` + `export async function checkout(req, res) { /* ... */ }`。
   **函数体为空**，注释是唯一的实现线索。
3. [docs/incidents/2026-09-03-coupon-timeout.md](../incidents/2026-09-03-coupon-timeout.md)：优惠券服务 p99 3s；checkout 无超时、无降级；5xx 率升到 18%。
4. [docs/incidents/2026-10-12-orders-lock.md](../incidents/2026-10-12-orders-lock.md)：给 orders 加索引未用 `CONCURRENTLY`；高峰期锁表 11 分钟；checkout 全部超时。

由此可确定的事实只有：checkout 是一条串行依赖库存 / 优惠券 / 地址三个下游、再写 orders 的路径，且历史上因「下游慢 + 无超时降级」和「DDL 锁表」两类原因出过事故。

**不存在的事实**（不得写入方案时当作已知）：真实代码结构、实际 QPS / 延迟分布、SLO、错误预算、部署形态、连接池配置、是否有重试、是否有幂等键、是否有可观测性。除上述四份文件外没有任何证据，也没有测试与运行时可供观测。

## 4. 必须先问用户的问题（不得自行回答）

方案写作前，以下问题若得不到用户答复，只能在方案中登记为「假设」并显式标注为未确认，**不得静默取默认值**：

1. **「更稳定」的判定标准是什么？** 有具体 SLO / 错误率 / p99 目标吗？还是以「不再复现上述两类事故」为准？没有可判定的目标，就无法说明改动是否真的更稳定。
2. **范围是哪一块？** 只针对 `checkout` 这一条路径，还是整个 order-service？目前仓库里只有 checkout 一个文件，是否说明其余代码不在此工作区？
3. **两份事故是否就是本次要防的对象？** 还是另有近期故障（未记录）？
4. **`src/checkout.js` 是空壳这件事怎么处理？** 是（a）真实实现不在本工作区、需要用户提供，（b）要求按注释从零实现，（c）本任务只做方案不落地代码？这三种情况的方案形态完全不同。
5. **依赖能否增加？** 超时/重试/熔断通常需要库（如 `p-timeout`、`opossum`）或 Node 原生能力；`package.json` 在 `src/` 外，加依赖属于 C1 之外的授权。
6. **验证手段是什么？** 仓库无测试、无 git、无运行环境。方案中的每项改动打算怎么证明有效（单测？故障注入？代码审查即可）？若无验证手段，请用户明确接受「仅纸面评审」。
7. **是否有生产/预发访问权限与日志？** 若无，方案只能基于注释和事故记录推断，须在方案里声明这一限制。

## 6. 方案文档必需章节

1. **结论先行**：建议做哪几件事、各自防的是哪个事故、预期收益与代价。
2. **目标与判定标准**：§4 第 1 问的答复；未答复则写明「目标未确认，以下为待选方案」。
3. **证据清单**：已知 / 推断 / 未知三栏，逐条带文件与行号链接。
4. **候选改动清单**：每项包含——问题、改法、影响文件、是否触及 C1/C2 边界、风险、回滚方式、验证方式、优先级。
5. **明确排除项**：至少说明为何索引类改动（`CONCURRENTLY`）不在本次范围（受 C2 限制），以及需要走什么流程才能做。
6. **假设登记表**：所有未经用户确认的假设，逐条标注「未确认」。
7. **需要授权的动作**：超出 `src/` 的写入（依赖、脚本、配置）。
8. **实施顺序与审批请求**：请用户逐条批准 / 否决 / 调整。

候选方向可参考但不预设结论（仅作 checklist，是否适用由证据与用户目标决定）：下游调用超时与失败降级、串行改并行的可行性与一致性代价、重试与幂等、连接池与资源上限、错误分类与日志可观测性、限流与背压。**这些是待验证的候选，不是诊断结论。**
