# 任务简报：AI 代码审查 — 团队采纳决策材料

| 项 | 内容 |
| --- | --- |
| 主题 | 团队是否引入 AI 代码审查，以及如何起步 |
| 当前阶段 | **探索/决策前**（用户明确表示"还没想好要不要用"，"说不清担心什么"） |
| 简报撰写 | 2026-11-06 |
| 执行者 | 后续接手的 agent |
| 交付物 | `docs/ai-code-review/decision-memo-v0.1.md`（主）+ 条件性附录 |
| 时间盒 | 单轮完成 v0.1，不等待用户回复 |

---

## 1. 用户的原始请求

> 我还没想好团队要不要用 AI 做代码审查，也说不清担心什么。你先直接给我写一份完整的推广落地方案吧，越完整越好。

## 2. 阶段判断：请求与阶段不匹配（本简报的核心）

用户要的是**推广落地方案**，但用户所处的是**决策前**阶段。这两者的前提条件不同：

| 推广落地方案需要的输入 | 当前是否具备 |
| --- | --- |
| 已决定"要做" | 否，用户明说还没想好 |
| 目标范围（哪个团队、多少人、多少仓库） | 未知 |
| 现有评审流程与痛点基线 | 未知 |
| 合规红线（代码能否出内网） | 未知 |
| 预算与采购权限 | 未知 |
| 决策人、时间窗、成功判据 | 未知 |
| 担心的具体风险（这决定方案要防什么） | 用户自己说不清 |

结论：**现在写"完整推广落地方案"，只能靠编造上述输入**。产出的文档会在第一个问题上被推翻（"我们代码根本不能上传"、"我们只有 6 个人，不需要推广方案"），用户拿不到可用东西。

因此本任务**不交付推广落地方案**，而是交付**能推动决策的等价物**：把"说不清的担心"变成一份可勾选、可验证的风险清单，把"要不要做"变成有判据的选择题，并给出一个成本极低的验证动作。推广方案作为**条件性附录**存在——只有当决策为"做"时才展开，且只展开到试点，不展开到全量。

用户说"越完整越好"。此处的"完整"应理解为**决策所需信息覆盖完整**（选项、风险、判据、验证路径四类齐全），而不是**执行步骤堆满**。简报要求执行者在文档开头用两句话说明这个取舍，不要默默降级交付。

## 3. 交付物规格

### 3.1 主交付物：`docs/ai-code-review/decision-memo-v0.1.md`

建议 1200–2000 字，结构固定为五节：

1. **我们要解决的问题**
   不写"提升代码质量"这类空话。列出候选痛点并标注"待用户确认"：漏检缺陷类型、评审排队延迟、评审人力集中在少数人、规范执行不一致、新人上手慢。每个痛点写一句"如果这就是你的问题，那么 AI 审查的哪一部分才对得上"。

2. **选项集（不是二选一）**
   至少四档，逐档写成本/收益/风险/退出成本：
   - A 不做，只做流程改进
   - B 只做辅助：PR 摘要、评论建议，不阻断合并
   - C 建议 + 人工裁决：AI 出结论，人决定是否拦
   - D 阻断式门禁：不通过不许合并
   外加一个正交维度：**采购 SaaS vs 自建/开源自部署**——这条由合规红线决定，单独成段说明分叉点。

3. **担心清单（本交付物的核心价值）**
   用户说不清担心什么，就给他一份能对着勾的清单。按类分组，每条包含【具体表现】【如何验证】【缓解手段】【不缓解的后果】：
   - 质量类：误报噪音、漏报、只会挑格式问题、对业务逻辑无判断力
   - 责任类：AI 提的错谁负责、评审权威被稀释、出事故后追责路径
   - 信任类：资深工程师抵触、被当成监控工具、评论语气引发对抗
   - 流程类：合并变慢、评论淹没真人讨论、开发者学会"哄过 AI"
   - 安全合规类：代码外泄、供应商训练数据条款、审计留痕
   - 经济类：按席位/按量的成本随规模失控、迁移成本与锁定
   - 度量类：指标被优化而非问题被解决（评论数、拦截数失真）
   末尾加一行：**"以上哪些是你真正在意的？勾 3 条，方案就按这 3 条设计。"**

4. **决策判据**
   写清"什么条件下做、什么条件下不做"，用可观测条件而非感觉。例如：若评审等待时长是主痛点且代码可出内网 → 直接试 B 档；若合规不允许代码出内网且团队 <10 人 → 自建维护成本大概率高于收益。判据要能被用户当场回答"是/否"。

5. **下一步（最小验证）**
   一个 2–4 周、单团队、可回滚的试点：范围、样本量、对照方式、观察指标（至少含 1 个反向指标，如合并时长变化）、**放弃条件**（什么结果就停）。明确写"这不是推广方案"。

### 3.2 条件性附录：`docs/ai-code-review/appendix-pilot-playbook.md`

仅在主文档第 4 节判据成立时展开。内容限于试点执行层：接入方式、评论规范与话术、人工复核规则、指标采集口径、复盘模板。**不写全员推广节奏、培训体系、组织变革**——那需要试点结果和真实组织信息，现在写就是编。

若判定当前信息不足以展开附录，就在主文档里写明"附录暂不产出，触发条件为：__"，不要产出占位空壳。

## 4. 允许与禁止

**允许的假设**（必须在文档开头集中声明为"本稿假设，需确认"）：
- 团队规模按 5–30 人写，用区间和"若…则…"分支覆盖，不锁定具体数字
- 不假设任何具体厂商、价格、产品能力对比结论
- 不假设行业基准数据（如"AI 审查能减少 30% 缺陷"），若引用必须标来源，无来源则不写

**禁止**：
- 编造团队现状、现有流程、合规要求、预算、决策人
- 编造厂商报价、ROI 数字、同行案例
- 用"业界最佳实践"替代具体判断
- 把附录写成全量推广方案来满足"越完整越好"
- 产出空章节、占位符、"待补充"堆砌

## 5. 验收标准

- [ ] 文档开头有阶段说明与假设声明，读者能一眼看出哪些是事实、哪些是假设
- [ ] 担心清单每条都有"如何验证"，不是只有形容词
- [ ] 第 4 节判据可被用户用是/否回答，不含"视情况而定"
- [ ] 第 5 节含放弃条件与至少一个反向指标
- [ ] 全文无编造的团队信息、价格、基准数字
- [ ] 附录要么按触发条件真实展开，要么明确标注不产出及触发条件

## 6. 交付时同步给用户的开放问题

以下问题阻塞"推广落地方案"，v0.1 不等回复即可产出，但必须在交付说明中列出（按影响排序）：

1. 触发这次讨论的具体事件是什么？（一次线上事故？评审积压？有人提了一嘴？）
2. 团队规模、每周 PR 量、当前平均评审等待时长、评审是否集中在少数几人？
3. 代码能否离开内网？是否允许使用外部 SaaS？
4. 谁做这个决定，希望什么时候定？
5. "推广"的对象是单个团队还是整个研发？预算量级有无上限？
6. 你认为什么样的结果算"用成了"，什么算"白折腾"？
