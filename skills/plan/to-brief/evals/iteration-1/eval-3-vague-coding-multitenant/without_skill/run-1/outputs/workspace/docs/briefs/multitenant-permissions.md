## 1. 目标（按可观察结果表述）

让 edu-platform 在共享库表的前提下，做到：

1. 每个请求都能确定唯一、可信的租户身份；
2. 任何跨租户的读、写、列表、导出、批量操作都被拒绝，且不泄露资源是否存在；
3. 租户内的功能访问由角色/权限控制，而非仅靠前端隐藏入口；
4. 上述行为有自动化测试证明，而不是靠代码评审口头保证。

「完整」在本简报中只表示**上面 4 条在已确认范围内闭环**，不表示要一次实现所有可能的权限模型。范围边界见第 6、7 节。

## 4. 可先行的工作（不依赖第 5 节决定，证据充分）

按顺序执行，每步独立可验收；任何一步失败即停下报告，不要跳步。

**P0. 建立可信基线**
- 运行 `mvn -q -DskipTests package`，原样记录失败输出（预计因缺失 `CourseMapper`/`Course` 失败）。
- 输出一份「当前可构建性 + 缺失文件清单」到 `docs/briefs/multitenant-baseline.md`。
- 若负责人提供完整仓库，改用完整仓库重跑，并更新 F1–F5。

**P1. 修掉已知越权点**
- 让 `pageTeachingCourses` 的查询同时受 `tenant_id` 约束（F4），并保留原有 `createBy` 语义。
- 若 `CourseMapper` 缺失，只补最小可编译桩并在简报中标注「桩，非真实实现」，不得假装完成。

**P2. 收紧租户上下文的生命周期**
- 过滤器必须在 `finally` 中 `clear()`；缺失/非法 `X-Tenant-Id` 必须被拒绝（状态码见 D4），**不得落到默认租户或 null 放行**。
- 异步/线程池/`@Async` 场景必须显式传递租户上下文，不能依赖 ThreadLocal 自动继承。
- 为 P2 写测试：同一线程连续处理两个不同租户请求，断言不串租户；请求结束后 `TenantContext.get()` 为 null。

**P3. 隔离回归测试（针对 F4 这类缺陷的通用防线）**
- 至少覆盖：按 ID 查详情、列表分页、按条件搜索、更新、删除——用租户 A 的身份操作租户 B 的数据，断言被拒绝。
- 断言「不泄露存在性」：跨租户访问返回与「资源不存在」**相同**的响应（具体状态码待 D4 定）。

P1–P3 的产出即使 D1–D7 全部未答，也是有价值且可回滚的；但它们**不等于**「完整权限体系」，不得据此宣称任务完成。

## 5. 阻塞决定（必须由负责人回答，执行代理不得自行假定）

每题给出选项与取舍，**不预先选定**。答复前，相关部分不得开工。

**D1. 租户身份从哪来？**
- (a) 继续信任 `X-Tenant-Id` 请求头（现状）：实现最省事，但任何客户端都能伪造租户 → 隔离形同虚设。仅在网关会**强制覆写**该头时才可接受。
- (b) 从已认证主体（Token/Session 中的 claim）解析，忽略客户端传入的租户头。
- (c) 两者结合：头仅作路由提示，与主体归属不一致时拒绝。
- 需要的信息：现有认证方式是什么？是否有 API 网关？

**D2. 隔离在哪一层强制？**（决定是否修订 ADR 0001）
- (a) 维持 ADR：service 层自觉 + 测试兜底。
- (b) 纵深防御：持久层拦截器/基类仓储自动注入 `tenant_id`，service 层仍校验。
- (c) 数据库行级安全（RLS）作为最后一道闸。
- 取舍：(a) 改动最小但同类缺陷会复发；(b)(c) 更稳但需要改基础设施、影响所有查询、迁移成本高。
- 需要的信息：持久层是 MyBatis 还是 JPA？表数量级？

**D3. 权限模型到哪一档？**
- (a) 仅角色（平台管理员 / 租户管理员 / 教师 / 学生）。
- (b) 角色 + 细粒度权限点（`course:read`、`course:publish`…）。
- (c) 在 (b) 上加数据范围（本人 / 本课程 / 本租户）。
- 需要的信息：现有角色清单、是否有菜单/按钮级权限表、是否需要自定义角色。

**D4. 跨租户与未授权访问的响应语义？**
- 404（隐藏存在性）还是 403（明确拒绝）？两者不能混用，否则本身就是信息泄露。
- 需要的信息：前端/调用方是否依赖特定状态码。

**D5. 是否存在跨租户的合法场景？**
- 平台运营方是否需要查看全部租户？是否需要「代客登录/切换租户」？若有，谁授权、如何审计？
- 若无，必须显式声明「不存在超级租户」，并让任何绕过路径都不可达。

**D6. 存量数据怎么处理？**
- 现有行是否都有 `tenant_id`？为空的行归属谁？是否需要回填脚本、唯一索引调整（如 `tenant_id + code` 唯一）？
- 迁移是否允许停机？是否允许改表结构？

**D7. 交付节奏与「完整」的验收边界？**
- 一次性交付全部，还是先 P0–P3 + 单租户核心模块（课程）跑通，再横向铺开？
- 是否需要审计日志（谁在何时访问了哪个租户的数据）？

## 6. 验收标准（在 D1–D7 答复后细化；以下为最低要求）

- [ ] A 租户用户对 B 租户资源的详情/列表/更新/删除/导出全部被拒，响应与「不存在」一致（D4）。
- [ ] 所有受租户约束的查询都能被证明带 `tenant_id` 条件：测试中捕获实际 SQL 或断言仓储调用参数，而非只读代码。
- [ ] 缺失、格式非法、伪造的租户标识均被拒绝，无默认租户兜底。
- [ ] 请求结束及异常路径下 `TenantContext` 必被清理；线程复用测试通过。
- [ ] 异步任务携带正确租户上下文。
- [ ] 角色 × 端点矩阵测试：每个角色对每个受保护端点有明确期望（允许/拒绝），且与实现一致。
- [ ] `mvn test` 在干净环境全绿；失败用例不得删除或跳过，只能修实现或改需求。
- [ ] 变更说明包含：改了什么、没改什么、D1–D7 的最终答复、未覆盖风险。
