结论：rung 2 的交付不成立——骨架屏是遮症状，不是修 bug。按阶梯的规矩退一层，回到 rung 1「登录页每次都能正常打开」，先把“什么时候白、白在哪一行”钉死，再谈整条链路。

**rung 2 为什么会跑偏。** rung 2 的 AI owns 我写的是「整条登录链路的稳定性」，这句话对执行方最省力的读法就是“加个兜底 UI 别让用户看见空白”。根因定位没有被写成交付物，于是它交了骨架屏。这是我这一层的写法问题，不是执行方偷懒。

**代码里已经能看见两条白屏路径**（[src/login.ts](src/login.ts)）：

- `mountLogin` 里 `await fetch('/api/session')` 没有 try/catch，也没有对 `res.ok` 的判断。请求失败、超时、或 `/api/session` 返回非 JSON（比如网关 502 的 HTML 错误页）时，promise reject，`root.innerHTML` 从头到尾没被赋值——页面就是白屏。这跟“偶尔”对得上：正常路径不触发，一抖就白。
- 就算请求成功，`root.innerHTML = s.user ? '' : '<form id="login"></form>'`，已登录分支渲染的是空字符串。会话还在（[docs/GLOSSARY.md](docs/GLOSSARY.md)：Redis 里 30 分钟 TTL），但前端拿到 user 后什么也不画——这也是白屏。

骨架屏两条都盖不住：如果它写在 `await` 之后，reject 时根本走不到；如果写在之前，它只会把“白屏”变成“永远转圈”，用户感受更差，而且把真因埋得更深。

**退回去之后，rung 1 的交付物应该是这样**，而不是补丁：

1. 白屏的可复现条件（哪种会话状态 / 哪类接口故障能稳定复现）；
2. 一条能指到具体代码行的根因结论，配上浏览器 Network + Console 的证据；
3. 修法候选，说明它各自能挡住上面哪一条路径。
