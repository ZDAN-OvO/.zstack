# Brief: 说清"团队要不要用 AI 做代码审查"，先出决策问题清单，暂不出推广落地方案

- Stage: think
- Source: 「我还没想好团队要不要用 AI 做代码审查，也说不清担心什么。你先直接给我写一份完整的推广落地方案吧，越完整越好。」

## Goal

- 服务于一个决策：团队要不要（以及在什么前提下）用 AI 做代码审查；产物是判断依据，不是执行方案。
- 首版产物是一份决策问题清单，把"说不清的担心"拆成能被团队回答的具体问题，并写明每问的答案指向哪种取舍。
- 下一步用途：清单被回答后，才进入"路线对比"（explore）或"推荐 + 落地方案"（decide / execute）。

## Context

- 用户自述尚未形成立场（"还没想好""说不清担心什么"），处于 think 阶段；此时写完整推广落地方案，只能写出任何团队都适用、因而无法决策的通用版。
- 用户点名要的是"完整推广落地方案"，属 execute 阶段产物，与当前阶段不匹配；本 brief 按 think 阶段重写 Done，不执行原请求。
- 工作区只有 `README.txt`（说明为 marketing / ops 临时工作区），没有团队资料、现有 code review 流程、工具清单、历史试点或评估记录。
- 团队规模、技术栈、现有人工评审怎么走、决策者是谁、有无代码外发或合规限制：全部未知，不得默认。
- 推断待确认："推广落地"指团队内部推行 AI 代码审查，不是对外营销推广。

## Materials

- 可用：用户本次请求原文；工作区 `README.txt`（仅说明工作区用途，不含业务信息）。
- 允许引用公开的 AI 代码审查工具与实践资料，但每条都要给可核查来源链接，并把"厂商宣称"与"第三方实测"分开标注。
- 团队侧数据一律以用户提供的为准；没有就写"未提供"，不估算、不补全、不拿行业均值冒充。
- 找不到出处的效果数字（检出率、评审耗时下降、返工率、案例收益）直接留空并标注"无来源"。

## Boundaries

- 不写推广落地方案：不出现试点范围、排期、里程碑、责任分工、培训计划、KPI、推广话术或预算表。
- 不替用户下"该用 / 不该用"的结论，也不做工具选型对比；选型和推荐属于后续阶段。
- 不假设团队规模、技术栈、现有评审流程、预算、合规要求；未知一律标"未知"，不写成条件句糊过去。
- 不编造或无出处引用效果数字，也不用厂商案例当成团队可复现的结果。
- 不用形容词代替判断标准（如"更高效""更安全"），每条担心都必须落成可回答的问题。

## Done

- 一份不超过一页的 Markdown 清单：6–10 个决定"是否用 AI 做代码审查"的问题，按价值 / 风险 / 成本 / 组织四组排列。
- 每个问题一行说明"为什么这问重要"，再加一行"答 X 意味着什么"，让答案直接连到取舍。
- 只交付清单本身；不附落地方案、排期、工具推荐或附录。
- 交付即停：等用户回答其中至少半数问题或明确"方向已定"，再谈下一步的路线对比或方案。

## Assumptions

- A1 读者是用户本人（用于自己想清楚并向团队 / 上级说明）；若实际读者是团队或管理层，Goal 的"判断依据"要改写成他们的决策语言。
- A2 "推广落地"= 团队内部推行 AI 代码审查，不是对外营销推广。
- A3 Materials 与 Boundaries 走默认规则：无来源数字不写、未知留空、不越出清单范围。
- A4 本 brief 按 think 阶段定稿；若用户改选 explore，Done 换成"2–3 条路线 + 各自权衡"，仍不写落地方案。

## Open questions

- Q1 阶段与交付物：接受把交付物从"完整推广落地方案"改成"决策问题清单"（think），还是先要"2–3 条可选路线 + 权衡"（explore）？
- Q2 读者与决策者：这份东西最终给谁看、谁拍板（你自己 / 团队负责人 / 上级）？决定清单的措辞与颗粒度。
- Q3 团队现状：团队人数与技术栈、现在 code review 怎么走（人工全量必审 / 只看关键模块）、有无代码外发或合规限制。
