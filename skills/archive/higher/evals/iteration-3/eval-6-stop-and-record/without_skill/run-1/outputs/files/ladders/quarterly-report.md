# quarterly-report — 阶梯记录

- 用途：周一管理层会，决定下季度预算分配
- 数据：BI 导出 CSV，现有 2 个季度
- 状态：Rung 3 定稿（用户改写），停在此层，交出去

## 阶梯

| 层 | 任务 | 状态 |
| --- | --- | --- |
| 0 | 把这季度数字填进上季度模板 | 已越过 |
| 1 | 解释变化、原因、下一步 | 接受 |
| 2 | 挑出最急的三个预算决策，各写支持与反对 | 接受 |
| 3 | **用两个季度的数据做出监测规则草案，标明回测不足**（原提案"评估季报是否该存在 + 设计日常监测流程"被用户改写） | 顶层，接受 |

## Rung 3 任务定义

- 目标：把"每季手填一次模板"换成"每天看关键指标，显著变化才提醒"。
- 交付物：**监测规则草案 v0**
  - 指标清单（选哪些、为什么）
  - 每个指标的提醒阈值与比较口径（环比 / 超区间 / 连续 N 天）
  - 触发后的动作：谁看、先看什么、多久内响应
  - 一页"回测不足"声明：2 个季度、无季节性、无同比、阈值是拍的
- 不在范围：接 BI、把监测真跑起来、改模板、改季报制度。
- 文件边界：除本文件和草案外，不改项目文件。

## 已知限制（写进交付物，不藏）

- 2 个季度 = 1 次季节循环都没有，做不出同比/季节性基线。
- 阈值只能给水平线，Q4 旺季的正常波动会误报；误报率无法事前估计。
- 2 季度也无法验证"提醒后动作"是否有效，只能靠上线后往前看。
- 因此草案定位是"待验证假设"，不是结论；需要 4+ 季度数据后再回测一次。

- 提醒发到哪：邮件、群、还是看板？
- 张紧度：宁可多报还是宁可漏报（决定阈值松紧）。
