## 直接建议

**默认选 Postgres**，除非你能说出一个具体的、现在就能验证的理由选 MongoDB。理由并不是“Postgres 更好”，而是：选错了 Postgres，你损失的是一条后来可以很轻松加上的路（JSONB、全文检索、向量 pgvector）；选错了 MongoDB，你损失的是事务边界和约束，后面要改数据模型，代价高得多。

## 真正值得看的判断标准

不看三个指标，反而先看下面三条：

1. **数据形状会不会在半年内反复变化**
   - 变化频繁、每条记录结构都不一样（比如爬虫结果、第三方 webhook 载荷、多租户自定义字段）→ 文档型确实更合适
   - 但请注意：Postgres 的 JSONB 能覆盖 80% 这类场景，而且还能混着用：固定的字段放列、可变的放 JSONB

2. **跨实体的操作是否需要原子性**
   - 转账、扣库存、订单+支付+状态机 → 需要跨文档、跨表事务和唯一约束，MongoDB 多文档事务虽然存在，但配置和性能成本不低，团队也容易用错
   - 如果只是为了写日志、发事件、追加记录 → 不需要考虑这条

3. **查询是由谁写的、能不能提前设计出来**
   - 查询模式在写代码之前就能列举出来（报表、筛选、排序组合）→ 关系型 + 索引更可预测
   - 查询模式完全不可预知，且以“按 id 取整个文档”为主 → 文档型更省事

## 常被高估的指标

- **性能 benchmark**：在几十万到千万量级，两者差距远小于你的查询写法和索引设计带来的差距，这一条基本不能用来选型
- **“无 schema 所以开发快”**：事实是 schema 会从代码层转移到应用层，只是没有数据库帮你挡
- **招人容易度**：都容易，不是区分点

## 需要你回答的三个问题

1. 核心实体大概有哪些？它们之间有没有大量“多对多、需要 join 的关联”？
2. 现在能列出前 5 个查询吗？（能不能列出来本身就是答案）
3. 团队里有没有人真的在生产环境运维过 MongoDB 副本集？

回答这三个问题后，答案基本就确定了。如果你的场景是“多租户 + 自定义字段 + 关系不多”，我可以帮你把 JSONB 方案和文档模型方案的具体 schema 都写出来对比。
