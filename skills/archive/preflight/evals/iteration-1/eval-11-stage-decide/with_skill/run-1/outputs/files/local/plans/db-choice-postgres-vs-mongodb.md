## Requirement

已知：两条标准同向，结论 = Postgres。下面的动作不是"再选一次"，而是把这个结论变成可被推翻、可被执行的。

Hand over: 一页决策记录 = 结论 + 决策规则（哪条标准权重更高、什么条件下翻转、看什么阈值），外加在真实 schema 上跑通的关键查询与一个事务场景
Fallback: 只交结论 + 三条翻转条件（一句"如果出现 X，就回到 MongoDB"），不碰数据
Depth: 不用"会不会 SQL"的感觉，用真实数据量化两个信念 —— (a) 关系密度：外键/多对多连接数、必须原子的写路径有几条；(b) 团队缺口：Postgres 的运维负担（备份恢复、大版本升级、连接池、慢查询定位）对比 Mongo 的（副本集、分片、无 schema 导致的数据漂移）。工具是 Postgres 的 JSONB + 事务 + 约束，对照 Mongo 的 $lookup 表达力与跨文档事务限制，不是对比文章
Stretch target: 让红队用 MongoDB 写出同一个最关键查询和同一个事务场景。写得通且不退化 → "强关系"这个信念被检验过，结论变软；写不出或退化 >5x → Postgres 赢得更硬
Range: 这个产出要做的动词：让人据此动手（决策）、让两个选项在同一把尺子上可比（评估）、让半年后的人能推翻它（审计）、防止拍脑袋（红队）
Crew: 数据库 SRE/DBA —— 算三年运维与故障恢复代价；应用架构师 —— 划事务边界与查询模式；技术负责人/招聘视角 —— 补 SQL 之外的技能 vs 承担 Mongo 运维风险；红队 = 一个只为 MongoDB 辩护的会话 + 一个反对双方（"两个都别选，先上托管服务"）
Judge: 你本人判业务与团队部分（这块你能直接判，够了）；技术部分跑通过滤器：在 Postgres 上真实数据跑通关键查询与事务场景（能跑 = 过）+ 红队逐条反驳 + 一个会话裁定哪些反对成立。判方法不只判结论：结论正确但没量化关系密度、没写翻转条件 → 不合格
Needs: 真实 schema 或脱敏数据样本（缺）、最关键的 3 个查询/读写路径（缺）、数据量与年增长（缺）、是否需水平写扩展（缺）、托管还是自建（缺）
