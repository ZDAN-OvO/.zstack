## Requirement

Hand over: 按原样交付报告；但真正要交的是**一个能扛住反问的判据 + 据此得出的方向**，报告只是它的外壳。
Fallback: 若拿不到自有赢单/流失数据，退为一页决策简报（判据、证据强度、在什么情况下结论反转），不出完整报告。
Depth:
- 原始材料：不是竞品官网，而是①你们的赢单/丢单记录与丢单理由②流失与降级原因③客服工单主题分布④销售被反问的原话⑤竞品**定价页结构**的时间快照（席位/计量/额度/免费额度）。
- 工具：投诉语料按时序编码（把 G2/Capterra 差评按「太贵」vs「难用」分类做趋势），定价页 diff，赢单表交叉编码——不是功能对比矩阵。
- Stretch: 先立一个可被证伪的断言（例：本客群「贵」的反对集中在多席位采购者，「难用」集中在单人试用者），再用你方未参与建模的那段管道数据去验证它。
Range: 报告要做的动作是①判定哪个 USP 对买家有决定权②让证据可被复核③经得起反向攻击。Crew：竞品情报（定价与包装取证）、定价经济（支付意愿与捆绑）、定位策略（品类框架）、买家研究（赢单/丢失编码）、红队（用同一批数据论证相反结论）。
Judge: 你本人能直接判（你认识买家）；方法层面加一个红队会话，专门攻击「便宜」与「易用」两个结论的证据链，命中即返工。
Needs: 你方赢单/流失/工单数据（缺，需授权）、竞品名单与客群定义（缺）、评价站点取样范围（缺）。
Proposed:
1. 交付物从「报告」抬到「方向 + 反转条件」——报告结构不变，结论必须可被证伪。
2. 把「易用 vs 便宜」当成买家**切换成本**的函数而不是二选一：先答「本客群里哪一项在触发比价」，方向自明。
3. Done 加一个 1 页论点+目录的 checkpoint，再展开全文（你在上一条里明确拒绝过中间稿，等你裁定）。
