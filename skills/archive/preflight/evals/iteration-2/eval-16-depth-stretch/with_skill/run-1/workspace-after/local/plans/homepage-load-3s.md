# Plan: 首页加载从 5 秒降到 3 秒

- Asked: "首页加载 5 秒，帮我优化到 3 秒"
- Stage: execute
- Date: 2026-11-10

## Requirement
Hand over: 用户能开始操作的那一刻（首屏可见 + 可交互）在真实用户分布里的 p75 不超过 3 秒，且有改造前后的同一口径数据为证 —— 而不是"某次在本机看到的 5 秒变 3 秒"。
Fallback: 在指定设备/网络档位上，用固定协议测得的实验室 LCP 3 秒；口径写死，不追字段数据。
Depth: 先量后改。原始材料是 trace 和 waterfall，不是"5 秒"这个结论：字段数据（web-vitals / RUM）分路由看 p75，再用 DevTools profile 找首屏真正阻塞的那一段，改最大贡献项，复测，再落到 CI 性能预算上防回退。省下的时长按贡献排序，不按"常见优化清单"批量套。Stretch target：Lighthouse CI 预算进流水线，超预算即失败，让 3 秒被守住。
Range: 交付物的动词 = 缩短"到可操作"的时间、不削减内容、并把证据摆出来。船员：性能工程师（trace / waterfall / 关键路径）、React 前端（渲染路径、代码分割、Suspense）、网络与后端（TTFB、缓存头、CDN、/api/session）、数据（分位数与样本量）。红队：一人专攻"3 秒是把活挪到首屏之后换来的、页面其实更卡"；一人专查改造是否抬高崩溃率与 SEO 损失。
Judge: 同一口径、同一档位复测的前后 trace + 字段分位数；判方法也判结果 —— 靠运气碰对数字但 waterfall 讲不通算失败，诊断正确但只到 4 秒算通过。红队两条反对意见需被逐条裁定。
Needs: 首页源码（本仓库只有 src/login.ts，首页不在这里）、构建配置（vite 配置缺失）、"5 秒"的测法与样本（设备、网络、冷热、分位、单次还是 p75）、登录态会话接口的线上表现、可复测的部署预览。以上均缺。
Proposed: ① Altitude 上移：把目标从"3 秒"改成"用户可操作时刻 + 明确口径"，否则 3 秒不可验证，也容易只优化了某个采样点。② Depth 加厚：先出 trace / waterfall 再动手，并把 CI 性能预算作为验收的一部分。③ Range 扩编：加网络/后端与数据两个角色，加红队；单靠前端改代码很可能改不动服务端那一段。
