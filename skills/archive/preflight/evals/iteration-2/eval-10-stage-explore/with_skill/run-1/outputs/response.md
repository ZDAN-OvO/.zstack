## 真正能区分这两个数据库的判断标准

| 判断标准 | 偏向 Postgres | 偏向 MongoDB | 这条标准是否真的常起作用 |
|---|---|---|---|
| 访问模式 | 跨实体任意组合 join、报表式聚合、临时分析 | 以“整块文档按 id/少量键取回后渲染”为主 | **常真的决定** |
| 事务与完整性 | 钱、库存、配额等必须原子 | 多文档事务从 4.0 起就有，但使用时需要遵守相应限制，并付出性能代价 | **常真的决定**（有金融语义时基本就定了） |
| 查询的不可预知程度 | 半年后会有人问“按 X 分组、关联 Y、再看留存” | 查询形态在建模时就固定了 | **常真的决定**，早期产品多数属于左列 |
| 写入的水平扩展 | 需要分区加应用层分片，或者上 Citus | 分片内建 | **很少真的决定**：多数项目达不到这个量级，到时也往往先做读扩展 |
| 团队与运维 | 谁能半夜被叫起来 | 同左 | **最常决定结果，也最常被漏掉** |
| schema 变更节奏 | 迁移要写、要有纪律 | schema 挪进应用代码，并不等于没有 schema，只是漂移换了个地方发生 | 两边都能忍，差异被高估 |
| 特化能力（全文/地理/时序） | pg_trgm、PostGIS、Timescale 通常够用 | Atlas Search 全文更强，但要上 Atlas | 有特化需求时才起作用 |

真正的取舍只有一句话：**Mongo 把建模决策推后，Postgres 把建模决策前置**。总量差不多，但后付的利息更高。而且这种不对称存在一个例外：在 Postgres 里早期用 JSONB 保留文档式的自由度，需要时再把字段提升为列；反过来，在 Mongo 里后来才发现要 join，就没有对等的退路。
