# 计划：季度回顾 → 每日监控（异常才提醒）

## 0. 先说硬约束（决定这份计划能承诺什么）

`data/q3-metrics.csv` 只有 **3 行月度汇总**（revenue / new / churn / nps）。用它**无法**证明"每日监控更早发现问题"——它连"日"都没有，也不含任何早期信号（激活、工单、使用深度）。所以：

- 这份计划分两段：**先补数据 + 用可追溯事件做回测**，再做**并行跑一个季度**。
- 如果拿不到日粒度历史（≥6 个月），"更早发现"就**不能事后证明**，只能做**前瞻对照**（从接入日开始双向记录）。这一点要提前跟老板讲清，不要用 3 行数据摆出一个假结论。

已有的可用锚点（来自 `notes/worklog.md`，是目前唯一的事件发生时间）：

| 事件 | 日期 | 性质 |
|---|---|---|
| 免费试用 14 天 → 7 天 | 2026-08 中旬 | 变更（可能是主因） |
| "太难上手"投诉明显变多 | 2026-09-08 | 症状首次被人工察觉 |
| QBR 给 VP 看 | 下周四 | 现有节奏 |

月度数已经能看到的恶化（滞后指标，事后才显形）：churn 12 → 19 → 24、new 41 → 35 → 30、NPS 38 → 31 → 27、收入 182k → 176k → 171k。注意 **8 月的 churn 跳升紧跟在试用缩短之后**——这正是"季报太晚"的样本：8 月中旬的变更，到 9 月底季报才被摆上桌。

## 1. 目标拆成可验收的三件事

1. **信号**：把"滞后指标"（收入/churn）换成能在周内动的**领先指标**，且每个信号有明确 owner。
2. **噪声**：任何时点**每周 ≤1 条**提醒，每条都带"谁、看什么、怎么办"。做不到就不是监控，是骚扰。
3. **证明**：对已知事件输出**首次发现日期对照表**（日报 vs 月报），并如实标注样本量。

## 2. 阶段与门禁

### G0 数据（第 1 周）— 不通过就不要往下做
- 取数：日粒度 12 个月（最少 6 个月）的试用注册、激活/上手完成、试用→付费转化、按主题标记的工单量、账号级使用深度、取消原因。
- 同时拉**变更日志**（产品/定价/试用期/客服人力），否则每次变更都会变成一次误报。
- 出口：一张按日对齐的表 + 变更日历 + 一份"缺哪些列"的清单。
- **不通过**（无日数据）→ 改为"从接入日起前瞻记录"，第 6 节的成功标准降级为观察而非证明。

### G1 指标与阈值（第 2 周）
候选信号（按领先性排序，宁少不滥）：
- 试用激活率 / 首周上手完成率（最领先，对应"太难上手"）
- 试用→付费转化率（7 日滚动）
- "上手困难"类工单占比与情绪（对应 9/8 那条）
- 账号使用深度下滑的账户数（churn 的前兆）
- 取消原因分类占比
规则：7 日滚动均值 vs 28 日基线，**连续 2 天越界**才触发；按工作日/周末分别定基线；最小样本量门槛，低于门槛只记录不提醒。
出口：信号定义表（口径、owner、基线、阈值、静默条件）。

### G2 提醒策略（第 2 周末）
- 分级：仅两级 —— **P1 找人（当天）**、**P2 进周报（不推）**。取消其他一切。
- 每条提醒固定四段：变化了什么 / 影响多大 / 建议动作 / 谁负责。
- 提醒预算：**每周 ≤1 条 P1**（超出即视为阈值调错，回头改规则而不是发）。
- 误报留痕：每条 P1 强制 24h 内回填"有效/无效 + 原因"，这是后面调阈值的唯一依据。

### G3 历史回测（第 3 周）— 这是"证明"的主体
1. 确定事件清单：工作日志 2 条 + 数据里能定位的拐点（如 churn 首次上扬的月份），**先去拿到确切日期**，日期模糊的事件不纳入统计。
2. 对每个事件算两个日期：
   - 日报首次触发日（用当时的阈值，不允许"看着答案调参"）
   - 月报/季报能看到的日期（月末或次月复盘日）
3. 输出：`事件 | 日报发现日 | 月报发现日 | 提前天数 | 期间误报数`。
4. 结论写法限定：写"在这 N 个已发生的事件上，平均提前 X 天，误报 Y 条"，**不写**"证明监控有效"。N 很小，就说很小。
5. 防过拟合：只用 8 月中旬变更**之前**的数据定阈值，之后的数据只用于验证。

### G4 并行跑一个季度（第 4 周起）
- 季报**照旧发**（`template.md` 的 Q3 格式不动），老板的阅读习惯不被打断。
- 并行期只加一条：每月的季报附一页"日报这个月报了什么、有没有用"。
- 并行期**不改**任何阈值去追业绩，只在误报复盘后调。
- 记录：P1 条数、有效条数、首次发现日 vs 季报发现日。

## 4. 边界落地（"不发垃圾提醒"）

| 反模式 | 本计划的约束 |
|---|---|
| 每天一条"指标播报" | 无异常不发；周报只汇总不发提醒 |
| 阈值一抖就响 | 连续 2 天 + 7 日滚动 + 最小样本量 |
| 已知变更引发的假警报 | 先查变更日历再发 |
| 提醒没有收件人 | 无 owner 的信号不进监控 |
| 提醒后无人回填 | P1 未回填视为流程故障，下周复盘提 |

## 5. 风险

- **样本太小**（3 个月、3 行）：回测只能算案例，不算统计。别把它包装成 A/B。
- **归因混淆**：试用期缩短与投诉上涨同期发生，监控能更早"看到"，但不等于能更早"解释"。解释仍需人工。
- **指标被优化**：一旦日报进考核，信号会失真。明确写"监控不用于考核个人"。
- **老板的注意力是稀缺资源**：P1 每周 ≤1 条是硬预算，超了就是产品缺陷。
