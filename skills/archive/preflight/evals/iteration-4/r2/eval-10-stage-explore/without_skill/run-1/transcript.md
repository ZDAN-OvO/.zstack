## 一句话结论
大多数新项目默认选 **Postgres**；只有当“整个应用的数据天然就是一棵/一堆文档、且结构高度不固定”时，Mongo 才明显更省事。

## 判断标准（按重要性排序）

**1. 数据关系有多复杂**
- 有 3 张以上表要 join、有事务要跨多个实体（下单+扣库存+记账）→ Postgres
- 数据基本是自包含的文档，一次读一个整体，很少跨集合关联 → Mongo 可以

**2. 结构稳定 vs 高度可变**
- 字段会频繁增删、每个记录结构都不一样（抓取的第三方数据、表单动态字段、CMS 多模板）→ Mongo 的 schemaless 是真实收益
- 业务字段相对稳定 → Postgres 的 schema 是保护，不是负担（配 `jsonb` 字段照样能存灵活部分）

**3. 一致性要求**
- 需要强一致、唯一约束、外键、多文档事务 → Postgres（Mongo 4.0+ 有事务，但语义和运维心智都比 PG 重）
- 能接受最终一致、以单文档原子性为主 → Mongo

**4. 查询形态**
- 报表、聚合、任意维度筛选、全文检索、地理查询 → Postgres（+ `jsonb` GIN 索引、`pg_trgm`、PostGIS）基本都能覆盖
- 只是“按 id / 按几个字段取文档” → Mongo 简单

**5. 团队与运维**
- 团队熟 SQL、公司已有 PG/RDS、要备份/监控/迁移工具链 → 选熟的那个，收益远大于理论优势
- 团队是 JS 全栈、想少写一层 ORM 映射、或已经在用 Atlas → Mongo 顺手

**6. 规模预期**
- 两者都能撑到很大。真正的分水岭是**写放大**和**数据量**：单机千万级文档 Mongo 分片省事；复杂分析型负载 PG 更强（需要时再加列存/数仓）

## 常见误判
- ❌ “Mongo 开发快”—— 现在 Prisma/Drizzle + PG 也很快，且省下后面数据一致性问题的返工
- ❌ “数据量大就得 Mongo”—— 大数据量更怕的是没设计好 schema 和索引，跟选哪个关系不大
- ❌ “PG 不支持嵌套”—— `jsonb` 就是为这个存在的，可以“关系为主 + 局部文档化”

## 实操建议
既然你还没定标准，先做一件事：**写下前 3 个核心用例的读写模式**（一次请求要读/写哪几个实体、要不要一起原子提交）。

- 答案里出现“一起提交”“要保持一致”“要 join”→ Postgres，不用再犹豫
- 答案里全是“取一个文档、改一个字段、塞回去”→ Mongo 是合理选择

补充一句：**Mongo 最大的成本不在写代码，而在两年后数据变脏、需要跨集合事务和报表的时候**。PG 最大的成本是前期建模要想清楚。新项目、经验不足时，PG 的风险更低。
