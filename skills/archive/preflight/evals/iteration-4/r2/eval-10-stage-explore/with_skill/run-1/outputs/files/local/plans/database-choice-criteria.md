## Requirement

Hand over（建议，待你裁定）: 一份**属于这个项目自己的**选型标准（每条标准带「Postgres 胜 / MongoDB 胜 / 打平」，再加一句「如果这条反过来，结论会翻转」）。
Fallback: 只给标准清单，不下判断。
Ceiling（超出可交付范围）: 由模型直接拍板并写好迁移脚本 —— 后果由你承担，且业务事实只有你有。
Depth: 不看产品对比表，看你的 workload：数据形状是否稳定、事务边界跨几条记录、查询模式、规模量级、团队能否运维、托管与备份成本。仪器 = 用你真实数据做一次百万行级读写 + 查询原型（Postgres JSONB 列 vs Mongo collection），而不是读博客。Stretch: 找出一个**能推翻结论的事实**，用你的数据验证它。
Range: 动词 = 让这个决定半年后不用重做 / 让团队能听懂并被说服 / 不把团队拖进没人会运维的系统。
Crew: 数据建模（查真实形状）、SRE（托管/备份/成本）、安全合规（审计、加密、最小权限）、红队（专门论证你选的那个会在哪先崩）。
Judge: 一个独立 session 当红队，只审**方法**（标准是否来自真实 workload、引用是否可查证），不看结论；最后一条由你判 —— 你能不能在两分钟内为一票辩解。
Needs: 项目是什么（缺）、数据形状样本（缺）、团队技能与已有基础设施（缺）、规模与增长预估（缺）、合规/托管要求（缺）。
