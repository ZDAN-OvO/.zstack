## Requirement

Hand over: 让某类问题从"季度末才知道"提前到"当周就知道，并且已经有人去处理"——不是交付一个每日监控脚本。
Fallback: 只做一族指标（新客上手失败 → 流失）的每日异常检测 + 回测报告，作为试点，报告里明说"这是试点，不是证明"。

Depth:
- 原始素材：日级事件流——按天的注册、激活/上手完成、带标签和日期的工单、流失发生日；以及 8 月中试用期 14 天→7 天的变更日，作为必须控制的混杂因子。
- 工具：变点检测 / 控制图（CUSUM、STL 残差）+ 前置期回测（lead-time backtest），在告警预算约束下报精确率与召回率，而不是"看图觉得有异常"。
- 专家动作（你没要求的那一层）：worklog 里 9/8 起"太难上手"工单明显变多，这是一个候选领先指标——去原始数据上测它是否真的领先流失 N 周，而不是直接假设。
- Stretch: 在留出的时间窗上，检测器比月度报表早 2–3 周报警，且每月告警数不超预算。只会响的检测器必须判失败。

Range:
- 动词：发现 → 解释 → 定向到人 → 验证。
- Crew：可观测性/SRE（告警设计与告警预算）、统计（变点+回测）、客户成功运营（工单分类、"上手难"具体指什么）、财务/RevOps（指标口径、月度结算噪声、季节性）、红队（专门想办法让老板收到垃圾提醒）。
- 红队那条正对着你的墙："不发垃圾提醒"。

Judge: 留出时间窗上的回测，同时评方法——幸运猜中要判失败，方法正确但差一点可以过；再加一场红队会话专门造误报，最后由你（或老板）裁决。

Needs:
- 有：data/q3-metrics.csv（仅 3 行月度汇总，7→9 月：收入 182k→171k、新客 41→30、流失 12→24、NPS 38→27）；notes/worklog.md（9/8 起上手投诉增多、8 月中试用期砍半、QBR 下周四）。
- 缺（阻塞）：日级数据；工单原始数据（含标签与日期）；流失实际发生日；变更/发版日历。
- 缺：告警预算（每月最多几条）、提醒抄送谁、谁负责第一动作。
