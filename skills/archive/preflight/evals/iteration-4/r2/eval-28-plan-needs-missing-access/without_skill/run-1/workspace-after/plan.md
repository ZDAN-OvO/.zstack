# Plan：季度回顾 → 每日监控（异常才提醒老板）

## 1. 目标与完成定义

**目标**：问题早发现——把"季度末才知道出事"改成"出事 1~2 周内知道"。
**完成定义**（来自你，拆成可判定项）：

1. **G1 证据关**：用历史数据回测，证明同一批历史问题，新机制比季报**更早**发现（中位提前 ≥ 30 天），且**误报 ≤ 4 条/月**。
2. **G2 并行关**：与季报并行跑一个季度，期间季报照常出、结论不冲突；并行期末做一次对照复盘。
3. **G3 切换关**：老板侧只收异常推送，不再靠季报发现趋势；季报降级为存档/对外。

G1 不过 → 不进入 G2，先改阈值/指标，不硬上。

## 2. 现实约束（必须先承认的）

- `data/q3-metrics.csv` 只有 **3 行月粒度**数据（2026-07 ~ 09）。**这份数据无法证明"更早发现"**：无日/周粒度，就没有"提前多少天"这个量；3 个点也谈不上基线。
- 所以 G1 的**前置动作是数据审计**：产品库 / 计费 / CRM / 工单系统里有没有可回溯 ≥ 4 个季度的日或周粒度序列。
  - 有 → 直接回测（本计划主线）。
  - 没有 → G1 延后：先 shadow 跑 1 个季度攒日粒度历史，再回测，再进 G2。**总工期从 1 个季度变成 2 个季度**，这点要现在就跟老板对齐，别到期末才发现。
- 现有数据已经有一条强线索，可作为回测的第一个测试用例（是假设，不是结论）：
  - 流失 12 → 19 → 24，NPS 38 → 31 → 27，收入 182k → 176k → 171k；
  - `notes/worklog.md`：**8 月中旬试用 14 天改 7 天**，9 月 8 日起"太难上手"工单变多。
  - 可检验的推断：真正的先行指标是**试用→付费转化率**，它应该在 8 月底就掉；而工单和流失是下游后果。若成立，日监控相对季报的提前量约 4~6 周。**这个数字必须由回测给出，不能由本计划断言。**
  - 反面教训：如果只监控收入/流失/NPS 这些**结果指标**，日监控也早不了多少——早发现靠的是先行指标。这是本计划的设计核心。

## 3. 指标设计

分两层，只有先行层能实现"早"。

**先行层（每日，进告警）**
- 试用注册量、试用→付费转化率（按注册周分组，7/28 天口径分开）
- 激活率（注册 3 日内完成关键动作的比例）
- 新手引导/上手类工单量与占比
- 付费页/定价页转化、取消页访问量

**结果层（每日算、低频告警）**
- MRR、新增客户数、客户流失数、**收入流失率**（churned MRR / 期初 MRR，不用裸计数）
- NPS（月粒度，只做趋势确认，不单独告警）

**指标纪律**：每个指标必须有①明确定义与分母 ②owner ③runbook（看到这条告警先查什么、48h 内做什么）。**没有 runbook 的指标不进告警**——这是"不发垃圾提醒"的第一道闸。

## 4. 异常判定（防垃圾提醒的机制）

- **基线**：同比同星期几的稳健基线（近 8 周同 weekday 中位数）+ MAD 离散度，不用均值/标准差（会被异常值带偏）。
- **持续性原则**：连续 2 个周期越界才告警（单点毛刺不告警）。
- **最小样本闸**：序列 < 8 周历史或分母 < 30 的，只观察不告警。
- **变化点检测**：对转化率这类比率，用 7 日滑窗 vs 前 28 日基线的双比例检验，避免小分母乱跳。
- **去重与冷却**：同一指标同一方向合并成一个 incident，24h 内不重复推；冷却期 3 天。
- **告警预算**：全局硬上限 4 条/月（老板侧 2 条/月）。超了就是阈值错，不是业务差。

## 5. 分级与路由（"异常才提醒老板"）

| 级别 | 触发 | 收件人 | 节奏 |
|---|---|---|---|
| L1 | 先行指标轻度越界 | 指标 owner | 即时，内部 |
| L2 | 先行指标持续越界 / 多指标同向 | owner + 你 | 即时 |
| L3 | 结果指标持续越界，且已有 L1/L2 佐证 | **老板** | 即时，附 3 行结论 + 建议动作 |
| 摘要 | 无异常 | 你（不发老板） | 周报一屏 |

原则：**L3 必须能回答"发生了什么、影响多少、建议怎么办"**，只报"数掉了"不发。老板侧总量 ≤ 2 条/月。

## 6. 执行步骤

**W1 数据审计（阻塞项）**
- 盘点各系统可回溯粒度与字段，产出 `data-audit.md`：哪个指标、从哪天起、什么粒度、能否重算。
- 明确写出"能证明"和"不能证明"的边界。

**W2 指标与基线定义**
- 落地指标字典（定义/分母/owner/runbook），先做先行层 5 个指标。
- 用现有月度数据跑通结果层口径，和 Q3 季报数字对账，误差必须为 0（否则口径有问题）。

**W3 回测（G1）**
- 在可回溯历史上重放每日判定，产出：
  - 每个历史事件（从 worklog/工单/事故记录里列全）的**首次告警日**与季报口径**发现日**，算提前天数；
  - 每月告警条数、精确率（告警后 14 天内业务确认真实问题的比例）、漏报数。
- 判定：中位提前 ≥ 30 天 且 误报 ≤ 4/月 且 无重大漏报 → 过 G1。
- 不过就调参重来；**连续两轮不过就说明"日监控早不了"，如实上报，别改完成定义蒙过去。**

**W4 影子运行（2 周）**
- 告警只发你和 owner，不进老板；每天人工核对告警对错，形成误报台账。
- 目标：误报清零或确认不可再降。

**W5 并行季度（G2）**
- 老板侧开 L3；季报 `template.md` 照旧出，不做任何删减。
- 每两周一次 30 分钟复盘：本周告警数、真/假、有无季报会漏掉的。
- 期末对照：同一季度，日监控 vs 季报，各自发现日、提前天数、误报数、老板被打扰次数。

**W6 切换决策（G3）**
- 达成 → 季报转存档/对外，日监控为唯一发现机制。
- 未达成 → 保留季报为兜底，日监控只做内部预警，写清原因。

## 7. 风险

| 风险 | 应对 |
|---|---|
| 无日粒度历史，G1 无法按期 | W1 就暴露，工期改为 2 个季度，先对齐预期 |
| 告警退化成人人无视的日报 | 告警预算硬上限 + 周度误报台账 + 无 runbook 不告警 |
| 只盯结果指标，早发现变成空话 | 先行指标为核心，回测里单独度量"若只监控结果指标能提前几天"作为对照 |
| 小样本/季节性误判 | 同比同 weekday 基线 + 最小样本闸 + 持续性要求 |
| 老板因一次误报失去信任 | 影子期 → 只发 L3 → 首月每条附人工确认标记 |
| 指标被优化到失真 | 保留结果层做交叉验证，指标定义变更走版本记录 |

## 8. 产出物

- `data-audit.md`（W1）
- `metrics.md` 指标字典 + runbook（W2，含 owner）
- `backtest-report.md`（W3，G1 判定书：提前天数分布、误报率、漏报清单）
- 运行中的告警配置 + `alert-log.md` 误报台账（W4~W6）
- `parallel-run-review.md`（并行期末对照，G2/G3 决策依据）
