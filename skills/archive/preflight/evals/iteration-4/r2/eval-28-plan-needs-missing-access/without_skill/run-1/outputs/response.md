核心判断三点：

1. **`data/` 里只有 3 行月粒度数据，证明不了"更早发现"**——没有日/周粒度就没有"提前多少天"这个量。所以第一步是数据审计，而且这是阻塞项：如果产品/计费/CRM 里回溯不到 4 个季度的日粒度历史，G1 就得往后挪一个季度先攒数据，总工期变 2 个季度。这点要现在跟老板对齐，别到期才发现。

2. **早发现靠先行指标，不靠结果指标**。worklog 里 8 月改试用期 → 9 月工单变多 → 流失 12→19→24，真正的先行信号是试用→付费转化率，大概 8 月底就该掉。如果日监控只盯收入/流失/NPS，比季报早不了多久。这个"提前 4~6 周"是回测要验证的假设，我没写进计划当结论。

3. **"不发垃圾提醒"做成机制而不是自觉**：同比同 weekday 的稳健基线 + 连续 2 周期才报 + 无 runbook 不进告警 + 全局硬上限 4 条/月，老板侧只收 L3（且 ≤2 条/月，必须带"影响多少 + 建议动作"）。

另外注意：G1 连续两轮不过就说明日监控确实早不了，那时按实情上报，不要改完成定义。
