- Stage: execute

## Requirement

已查事实（不需要你再确认）：CSV 按总量排名为 TypeError 789 次（2.3.0 412 + 2.3.1 377）、ChunkLoadError 88、RangeError 19。
榜首是 `TypeError: Cannot read properties of undefined (reading 'name') at login.ts:5`，对应 `src/login.ts:5` 的 `renderForm(s.user.name)`。该函数没有 `res.ok` 检查、没有 token 判空、没有 `.catch`。
**它跨版本存在（2.3.1 仍 377 次）**，所以不是版本回归，而是每次会话响应缺 `user` 就必然崩。

- Hand over: **让会话加载的每条失败路径都落到一个有定义的界面状态（未登录表单 / 加载中 / 报错），并附上先红后绿的回归测试** —— 而不是只在这一行加 `?.`。
- Fallback: 只给 login.ts:5 加空值保护，崩溃数归零但用户会看到 `undefined` 表单。
- Ceiling（不由我们持有）: 「登录页永不白屏 / 所有崩溃发布前拦住」。仓库里只有 `login.ts`，没有组件树可挂 error boundary，也没有监控与发布权限。
- Depth: 最原始的材料是这份**聚合计数 CSV**，没有堆栈、没有响应样本，所以「为什么 `user` 缺失」无法只靠日志定论 —— 要按契约推。专家动作（你没要求的那层）：先分清是 `s.user` 为空还是 `s` 本身不是 JSON，两种要不同的处理；再 grep 出所有消费 `/api/session` 的地方，避免只修一处。工具用 vitest + 假 fetch 造响应形状，不是改成表格看一眼。
  Stretch: 写测试先复现 412/377 的形状（红），修完转绿；再用**写测试时没见过的形状**（204 空体、HTML 错误页让 `json()` 抛、`{user:null}`）验证仍不崩。
- Range: 交付物的动词是「让登录页停在可用状态并说清为什么」→ 前端可靠性（修 + 定契约）、测试（回归夹具）、安全评审（`innerHTML` 注入 `name`、`Bearer null`）、红队（见下）。
  红队预登记的两条质疑：① 「最多」按日峰值还是按总量算，结论是否会变；② 只加 `?.` 是把崩溃换成静默错误，指标变好而体验没修 —— 这条必须能被判失败。
- Judge: 仓库现在跑不了 `npm test`（package.json 无 devDependencies、无 node_modules）。首选判法：装 vitest + 假 fetch，判「有先红后绿的测试」和「未见过形状仍不崩」，好方法+坏结果和侥幸对都要分开判。若你不允许加依赖，退化为：另开红队会话只读 diff 逐条走崩溃路径，再由第三个会话裁定红队异议。
- Needs: 【缺】`/api/session` 的真实失败响应样本与后端契约；【缺】vitest 及依赖安装许可；【缺】日志里出现的 `cart.ts` 在 `src/` 不存在 ⇒ 仓库是片段，无法支持「全站」口径；【缺】git（无版本对比、不可回滚）；【有】CSV 计数与 `src/login.ts`。
