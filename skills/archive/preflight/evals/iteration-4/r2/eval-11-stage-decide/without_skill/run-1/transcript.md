ASSISTANT: **选 Postgres。这两条标准指向同一个答案，没有需要权衡的地方。**

理由：

1. **强关系数据** —— 外键、JOIN、多表事务、唯一约束，这些是 Postgres 的原生能力；在 Mongo 里要靠应用层手工维护一致性（denormalize + 双写 + 补偿逻辑），出错是迟早的事。
2. **团队只会 SQL** —— Postgres 的学习成本≈0，现有 SQL 技能、ORM、BI 工具、`psql` 全部直接复用。换 Mongo 意味着团队要同时学：文档建模思维、aggregation pipeline、`$lookup`、副本集/分片运维 —— 在“已经有了正确工具”的情况下额外付两份学费。

补充一点常见的误判：如果纠结的点是“有些字段结构不固定”，那不需要 Mongo —— Postgres 的 `JSONB` + GIN 索引能覆盖大部分半结构化场景，而且还能和关系表放同一个事务里。

Mongo 真正合适的场景是：单文档为聚合根、schema 天然嵌套、写入吞吐极高、几乎不需要跨实体 join。你的描述里三条都不成立。

**结论：Postgres，不用再评估了。**
