## 先说默认答案

**没有强理由就选 Postgres。** 它不只是关系库：`jsonb` 能存半结构化文档，还能建索引、做 `jsonb_path_query` 查询，也支持全文检索、数组、range 类型、地理（PostGIS）、向量（pgvector）。你说的"文档模型"大部分需求它能覆盖，同时还能在需要时用事务和外键。

MongoDB 值得选的场景比较窄，通常是：写入模式极为无定形、单体文档天然完整（如事件流、CMS 页面块）、或者明确的水平分片需求。

## 真正决定选型的 5 个问题

1. **数据有没有强一致的关联？** 有用户/订单/权限这类多表 join 和事务需求 → Postgres。这是最硬的分水岭，MongoDB 的事务能力有，但跨集合 join（`$lookup`）和长期演进会很别扭。
2. **schema 会变多快？** 如果是"字段天天变、每个文档结构不同"（如第三方 webhook 载荷、抓取结果）→ 文档模型省心。如果只是"加字段要发 migration"，那其实不是问题，`ALTER TABLE` 很快。
3. **查询是"按 id 取整个对象"还是"多维度筛选聚合"？** 后者（报表、统计、任意组合过滤）→ Postgres 的 SQL 优化器和索引能力优势巨大。
4. **团队谁能维护它？** 备份恢复、慢查询排查、扩容——团队里谁真的会 MongoDB 的运维？很多时候这是唯一决定性因素。
5. **规模预期？** 单机 Postgres 撑到 TB 级、几万 QPS（读多可加副本）没问题。若你预期"从第一天就要跨地域多写"，再考虑 Mongo 分片或干脆看 CockroachDB/Spanner 类。

## 两个常见误区

- 「Mongo 无 schema = 开发快」：schema 没消失，只是从数据库挪到了应用代码里，且随机出现，半年后数据不一致的成本更高。
- 「Postgres 不适合 JSON」：`jsonb` + GIN 索引足够用；混合模型（核心字段列化 + 扩展字段 jsonb）往往是最优解。
