# Plan: 首页加载从 5 秒降到 3 秒

- Asked: 首页加载 5 秒，帮我优化到 3 秒
- Stage: execute
- Date: 2026-11-10

## Requirement
Hand over: 首页在约定机型/网络下 P75 加载 ≤3 秒，并且带上能守住的防线：性能预算进 CI + 真实用户监控（RUM），变慢在发版前被拦住，而不是只改这一次。
Fallback: 先测出真实基线并拆账（TTFB / 接口 / 资源下载 / 解析执行 / 渲染），只修占比最大的那段，用同一套测量复测到 3 秒。
Depth: 原始材料取真实用户 RUM 事件（机型、网络、地域、缓存冷热）和完整 waterfall/HAR，而不是一次秒表读数。仪器用 web-vitals/RUM、固定机型的 WebPageTest/Lighthouse 冷缓存、bundle 分析、Server-Timing、CDN 命中率；比 P50/P75/P95 分布，不比单次最好成绩。专家先问"5 秒花在哪一段"——已查到的线索：`src/login.ts` 的表单要等 `/api/session` 返回后才 `innerHTML`，首屏很可能卡在接口而不是包体积；`logs/crashes-2026-11.csv` 显示 2026-11-01 有 88 次 ChunkLoadError。Stretch: 不要 3 秒，要 P75 下 1 秒出可用首屏；并用 waterfall 检验"慢在 JS 体积"这个假设，允许推翻它。
Range: 交付物不是"一个 3 秒的首页"，而是：用户尽快看到可用内容并愿意留下；团队比用户更早发现变慢。动词 = 测量、定位、削减、验证、守住、同步。Crew: 性能工程师（关键路径、性能预算）、RUM/数据（分机型分网络的分布）、基建/CDN（TTFB、缓存命中、压缩）、前端构建（拆包、预加载、缓存头）、体验设计（先渲染什么才算"加载完"）；红队一名，只在低端安卓 + 冷缓存 + 慢 4G 上复现并试图推翻"3 秒"，再由一个独立 session 裁定哪些反对成立。
Judge: 外部判定 = 发布后 7 天的真实用户 P75（按约定机型/网络切片），加 PR 上的性能预算检查；本地一次跑分不算数。方法也判：靠热缓存桌面跑出的 3 秒算失败，方法对但差 200ms 算通过。没有 RUM 时退化为固定配置冷缓存跑 5 次取中位数，配置入库。
Needs: 首页源码（本工作区只有 `src/login.ts`，没有首页文件）；"5 秒"的出处（谁的设备、什么网络、哪个指标）；RUM 或加 web-vitals 的权限；可复现环境（staging/线上 URL）与构建发布权限；支持的机型/网络清单。缺的项已标出，等你确认。
Declined: 暂无，等你逐条裁定。

Context: 已核对的事实：版本 2.3.1；页面渲染依赖 `/api/session`；仓库里没有任何性能数据、没有首页源码；`vite`/`vitest` 只在 scripts 里，未装依赖，本地构建不可复现。待你补：首页指哪个页面、用户主要在什么设备和网络、最近改过什么。

Boundaries: 待你写。候选（请确认或改写）：不为数字牺牲功能与可访问性；不新增第三方脚本；不改后端接口契约；不接受"只在测试机上快、真实用户没变"的优化。
