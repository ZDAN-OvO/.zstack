- Stage: execute（越界到 decide：这份东西的用处是让 VP 在会上做取舍）
- Date: 2026-11-10

## Requirement

**Handover: 做出"三个决定"这一层**——每个决定带取舍、成本、不做的后果，并标出它依赖哪条证据（有一手数据支持 / 目前只是假设）。
**Fallback: 只讲变化与原因**，把决定留空成"需要 VP 拍板的问题清单"。

**Depth**：三行月度数不能证明原因。专家动作是**把变化拆成驱动因素**（新增 × 留存 × 客单价），并把「8 月中试用期 14 天 → 7 天」当成一次自然实验：变更前后分群对比试用到付费转化与首月流失。
> 事实：8 月中改试用期 → 9/8 起"太难上手"投诉增多 → 同期流失 12→19→24、新增 41→35→30、NPS 38→31→27、收入 182k→176k→171k（`data/q3-metrics.csv`、`notes/worklog.md`）。链条方向与故事吻合，但这是相关，不是因果。
**Stretch target**：用现有行做出一个**可被推翻**的因果假设，并写明"如果 X 数据是这样，我这个解释就错了"——而不是给出一个无法被否证的叙事。
> 注意：变更前只有 7 月一个月基线，n=1，前后对比本身就弱。这一点要写在回顾里，不能藏。

**Range**：动词是 让 VP **相信**数字是真的 → 让他**看懂**为什么 → 让他**选**。三个字段各有一手：
- 增长分析（驱动因素分解、cohort）
- 客户成功（工单里"太难上手"到底在说什么）
- 红队（专门攻击因果链和"这个决定下季真能执行吗"）

**Judge**：两条自检 + 一个外部会话。
1. 脚本把正文里每个数字回算到 `data/q3-metrics.csv`，对不上即失败；
2. 每条因果陈述必须挂到具体数据行，否则必须显式标注"假设"；
3. 红队会话攻击因果与可行性，再由一个会话裁定。评的是**方法**（结论是否被证据允许），不是故事讲得顺不顺。

**Needs**（⚠️ 缺）：分群留存 / 试用到付费转化 / 工单分类计数 / 8 月前更长的基线。这些没有，原因部分只能到"假设 + 需要什么证据"。
**Declined**：暂无（等用户裁）。
