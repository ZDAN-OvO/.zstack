# Plan: Postgres 还是 MongoDB

- Asked: 「我在 Postgres 和 MongoDB 之间选。标准就两条：团队只会 SQL；数据强关系。帮我定」
- Stage: decide
- Date: 2026-11-10

## Requirement

Hand over: 结论先给 —— 按你这两条标准，Postgres。两条各自独立都指向它；MongoDB 的赢面（schema 灵活、整文档读）不在你的标准里，而它在 Postgres 里可以用 JSONB 局部买回来。真正要交的不是库名，是**决定记录 + 3~5 个核心实体的参考 schema + 约束**，让团队能说「这个我们跑得动」。

Fallback: 只交一页决定记录（选 Postgres 及理由）+ 一张实体关系草图。

Depth: 把你那句「数据强关系」从形容词变成证据 —— 要的是**真实访问模式清单**（谁在什么时候读什么、一次读几行/几个实体、写多还是读多），不是实体图。工具是数据库自己的：外键与约束覆盖、`EXPLAIN` 下的关键路径、JSONB 承接非关系尾巴的边界。Stretch target：把你们最常用的 10 条查询落到 3 张表上跑一遍；如果其中有 6 条其实是「按键取整个文档」，那才是 MongoDB 唯一真正赢的地方，也才知道要不要给它留口子。

Range: 交付物要产生的动词是「团队敢接、运维敢值班、三个月后加字段不用开会」。crew：数据建模/DBRE（schema 与约束）、运维（备份、升级、谁 on call，Postgres 和 Mongo 在这上完全不同）、红队（替 MongoDB 打最强一版：文档式读写、频繁改 schema、写入吞吐）。两条标准同向指一个答案，说明这个决定还没被真正攻击过 —— 红队是这次的核心。

Judge: 会话外的红队 + 裁决两段（红队只准为 MongoDB 辩护，第三段只裁「这些理由是否成立」），外加一次可自检的检验：用你们的真实查询清单在原型 schema 上回放，看是否出现键值/文档式热点。若查不出访问模式清单，就退回你自己审 schema —— 你能直接判断这个 schema 像不像你们的业务。

Needs: 真实访问模式清单（缺，最关键）、现有实体/表结构导出（缺）、部署约束（托管 PG 还是自建、谁运维、数据量级、上线时间窗）（缺）。三项都缺，红队会打空。

## Task

Purpose: 待你回答 —— 「选库」是手段。这个选择最后要保证的是什么？（例：N 周内上线且团队能自己运维 / 不再为改 schema 卡住 / 数据一致性不能出错）
Context: 待你回答 —— 团队几个人、有没有人碰过运维、现有数据从哪来、部署在哪、多大、赶不赶时间。
Materials: 一手——真实访问模式清单、现有 schema 导出、部署与运维约束。**禁用**：「X vs Y 2025」类对比文、通用 benchmark、厂商文档里的性能页 —— 它们不认识你的数据。空缺：以上三项一手材料都还没拿到。
Boundaries: 待你确认这三条是不是「不要」——① 不要给我 benchmark 对打；② 不要建议换掉团队现有栈；③ 不要给 Postgres+Mongo 双库方案。
Done: 一页决定记录（选谁、为什么、什么条件下会翻案）+ 核心实体 schema 含外键与约束。Checkpoint：先只给决定记录和实体关系草图，你点头我再展开完整 schema 与查询回放。
