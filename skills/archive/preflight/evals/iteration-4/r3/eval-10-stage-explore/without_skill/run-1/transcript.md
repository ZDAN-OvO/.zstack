## 没想好标准时的默认答案：Postgres

理由不多，但足够硬：

- 关系、约束、事务是**默认能力**，不是后期补的。MongoDB 从开始就接受多文档事务，到 4.0 才补齐，且需要副本集。
- JSON 场景不吃亏。`jsonb` + GIN 索引能覆盖绝大部分“我需要灵活 schema”的需求，还能跟其他表 join。
- 退出成本低。数据在一个 SQL 库里，换 ORM、加读副本、上分析、加全文检索（`tsvector`/pgvector/ParadeDB）都是加法；MongoDB 想往关系模型走是重写。
- 生态、托管、招聘、运维经验都更厚。

## 真正能把它翻成 MongoDB 的标准（就这几条）

1. **数据本质是嵌套文档，且几乎总是整篇读写**。典型：CMS 页面、事件/日志负载、用户配置、问卷答案。聚合根清晰、不做跨文档 join。
2. **写入量极高且 schema 天然稀疏多变**，字段集合按文档类型差异极大，关系模型会变成 EAV 地狱或几百列空值。
3. **明确的水平扩展需求**，单机/单主扛不住，且分片键能自然选出来（MongoDB 的 sharding 比 Postgres 的声明式分片成熟）。
4. 团队已经熟 MongoDB，且这个系统不是账务/订单类核心域。

注意：这些多数是“现在就能确定”的事实，不是“以后可能会”。如果是“以后可能灵活”，那答案是 Postgres + `jsonb`。

## 看起来重要、其实不构成理由的

- “表结构还没定” → 前三个月用迁移改 SQL 表结构完全没问题，且比事后清理脏数据便宜。
- “MongoDB 开发快” → 原型阶段快，关系变复杂后慢的是应用代码，不是数据库。
- “我们不需要事务” → 几乎总是错的，只是还没碰到。涉及钱、库存、权限、幂等的地方必须有。
- “JSON 存储灵活” → `jsonb` 一样灵活，且能选择性加约束。

## 需要你自己回答的 5 个问题

1. 实体之间有关系吗？需要按关系查询/聚合吗？（≥3 类实体互相关联 → PG）
2. 有账务、库存、权限、订单这类一致性敏感逻辑吗？（有 → PG）
3. 查询是“给我整篇文档”还是“给我满足条件的行/聚合”？（后者 → PG）
4. 现在和 18 个月后的数据量、QPS 各是多少？（Pg 单机很能扛，别过早分片）
5. 团队更熟哪个？不熟的那个谁维护？（运维成本常被低估）

前 3 题有一个答“PG”，就用 PG。只有 1、2 都答“文档/无关系”且第 3 题答“整篇”时，MongoDB 才值得认真比较。
