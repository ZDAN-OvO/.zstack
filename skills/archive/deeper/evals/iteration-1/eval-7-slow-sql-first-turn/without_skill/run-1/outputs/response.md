不过在补材料之前，有个判断得先说清楚：200ms → 900ms 是 4.5 倍的**跳变**，不是"一直慢"。跳变几乎总有一个变化点（发布、DDL、数据量、统计信息、DB 参数、流量结构），而不是 SQL 本身写得不够好。直接按"重写 SQL"去改，很容易改了一堆却没碰到真正原因。

建议按成本从低到高查：

1. **先确认是不是这个接口独有**。全站 P99 都涨 → 方向在 DB / 连接池 / 网络，不在 SQL 文本；只有这个接口涨 → 才收窄到这条代码路径。
2. **找变化点**：第一次变慢的准确时间，对一下发布记录、DDL、表数据量、DB 参数（work_mem、连接数、最后一次 analyze 时间）。
3. **看请求放大**：这个接口一次请求到底打了几条 SQL？如果条数变多了（N+1、循环里查），那是代码回归，单条 SQL 再怎么调也没用。注意慢日志是按单次耗时排序的，会漏掉"单次 5ms 但一次请求调 200 次"这种。
4. **最后才轮到单条 SQL**：`EXPLAIN (ANALYZE, BUFFERS)`，区分是计划变了（走错索引 / 退化成顺序扫）还是计划没变但数据量涨了。这两种修法完全不同。
